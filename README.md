# 大家さんの決算メーカー（仮）

## 1. サービス概要

- 管理会社に物件を任せている会社員大家のための、確定申告書類の作成支援アプリです。
- 月次収支報告書に載っている入居者ごとの賃料・礼金・敷金などを登録すると、申告上の計上年月に沿って集計し、青色申告決算書の「不動産所得の収入の内訳」にそのまま転記できる一覧を作成します。
- 年に1回まとめて行っていた転記と集計を、毎月数分の登録に変え、確定申告を迷わず終わらせられるようにします。

---

## 2. このアイデアはどこから生まれたか

### 2-1. きっかけとなった体験・感情

- **いつ**：確定申告の時期。
- **どんな状況で**：会社員として働きながら、管理会社に委託してアパートを1棟所有している。管理会社から毎月届く月次収支報告書を見ながらExcelに転記し、青色申告決算書を作っている。
- **何が大変だったか**：
  - 同じ部屋でも、入居者が替わると家賃や敷金が変わる。
  - 年の途中で入居・退去した人は日割りになり、金額が月ごとにバラバラになる。
  - 12か月分の報告書から、入居者ごとの年額を拾い集めて足し合わせる作業に、毎年10時間ほどかかる。
- **どんな気持ちになったか**：とにかく面倒。忙しい年ほど後回しになり、締切ギリギリに追い込まれる。

### 2-2. なぜそれが「気になった」のか

- 税金に関わる数字は、ミスが許されないので確実にしたい。
- 同じ作業を毎年繰り返すことが嫌い。毎年同じことをしているなら、仕組みで解決できるはずだと思った。
- 10室の自分でもこれだけ手間がかかる。部屋数や入退去が多い大家さんは、もっと大変な思いをしているはずだと感じた。
- 本業でLLMを活用したアプリケーションのPdMをしており、「報告書の読み取りから決算書の作成まで、LLMでつなげられるのではないか」と考えた。

## 3. 課題の整理

### 3-1. 表に見えている困りごと

月次収支報告書からExcelへの転記と、入退去の追跡に手間がかかる。

### 3-2. 本当に解決したい課題

- **なぜ？** → 報告書は「月ごと・部屋ごと」にまとまっているが、決算書では「入居者ごと・1年分」で書く必要があり、データを手作業で組み替えるしかないから。
- **なぜ？** → 入居者の入れ替わりや家賃・敷金の変更を1件でも見落とすと合計が合わなくなり、すべての報告書を見直すことになるから。
- **なぜ？** → 年に1回まとめて片付ける作業になっているため、忙しい年ほど後回しになり、締切直前に焦って作業することになるから。

→ **本当に解決したい課題**：
会社員大家が、面倒な転記と集計を後回しにし続け、締切直前に焦りながら「ミスできない数字」を手作業で作っていること。

## 4. 想定ユーザーについて

### 4-1. 想定しているユーザー

**「管理会社に委託してアパートを経営し、確定申告を自分で行っている30代後半〜40代の会社員大家」**

年齢設定：
- 年齢：30代後半〜40代
- 理由：不動産投資を始められる資金があり、手間を減らすツールにお金を払う余裕がある世代。一方で、本業では責任ある立場にあることが多く、まとまった時間を取りにくい。

生活・状況設定：
- 生活・状況：平日は本業があり、申告作業は休日にまとめて行う。賃貸管理は管理会社に任せており、手元に届く情報は月次収支報告書だけ。確定申告は税理士に頼まず、自分で行っている。
- 理由：入居者の情報が毎月の報告書に分散しているため、年間の集計を手作業で行っている。アプリに月次データを登録すれば、入居者ごとの年額を自動で集計できる。

環境設定：
- 環境：PCで報告書とExcelを行き来しながら入力している。
- 理由：Excelでの集計をなくし、決算書と同じ並びで結果を表示することで、転記するだけで済むようにする。

### 4-2. 自分とユーザーの距離

- **自分自身**

→ 毎年この作業を自分で行っており、どこで手間がかかり、どこでミスが起きやすいかを身をもって知っているため。

### 4-3. 実際に使われる可能性について（需要・存在確認）

- **まず最初に使ってくれそうな人**：自分自身。周りに同じ立場の大家はいないが、部屋数が多い大家さんほど転記・集計の手間は大きくなるため、需要はあると考えている（→ 8章の懸念点②）。
- **思い出す場面**：管理会社から月次収支報告書が届いたとき／確定申告の準備を始めるとき。
- **今代わりに使っているもの**：Excel。
- **置き換えてまで使う理由**：Excelでは、入退去や家賃・敷金の変更を毎年自分で追いかけて集計し直す必要がある。このアプリなら、前月から変わった部分だけ直して登録すれば、決算書の形に集計される。

### 4-4. ユーザーがサービスを導入して利用するまでのイメージ（導入・継続の流れ）

- **知る・思い出すきっかけ**：確定申告の準備を始めたときに「今年もあの作業か」と思う。
- **最初の一歩**：物件・部屋・入居者を登録し、手元にある月次報告書の金額を登録する。
- **使い続ける理由**：報告書が届くたびに1か月分を登録しておけば、確定申告の時期には集計が終わっている。翌年は入居が続いている人の情報をそのまま使えるため、続けるほど楽になる。

## 5. 既存サービス・競合調査

### 5-1. 似たサービスの調査

- **サービス名**：大家さんのための超簡単！青色申告
  - URL：https://oyasan.kantan-aoiro.net/
  - どんなことができるか：大家さん向けの青色申告ソフト。「家賃管理表」に入居者ごと・月ごとの入金を入力すると、帳簿への自動仕訳と、年間集計・「収入の内訳」への反映ができる。
- **サービス名**：やよいの青色申告 オンライン
  - URL：https://www.yayoi-kk.co.jp/
  - どんなことができるか：入居者ごとに月額と契約期間を登録すると、「収入の内訳」の年額が自動計算される。実際の金額と異なる場合は自分で修正する。
- **サービス名**：Propiti
  - URL：https://propiti.jp/
  - どんなことができるか：管理会社の収支レポートなどのPDFをAIが読み取り、複数物件の収支を一元管理できる。

### 5-2. それでも自分が作りたい理由

- 会計ソフトは、帳簿付け（仕訳）や経費の管理まで含めた多機能なものが中心で、「収入の内訳」を作りたいだけの自分には機能が多い。
- やよいの青色申告 オンラインでは、年額は契約期間から計算されるため、日割りや入居者の交代があった月は、結局自分で金額を拾い直して修正する必要がある。
- 大家さんのための超簡単！青色申告は年間集計までできるが、入力は入居者ごとの欄に月ごとに行う形式。一方、手元の月次報告書は「1か月分・全室」が1枚に並んでいる。報告書と同じ並びで入力できれば、転記の手間をさらに減らせると考えた。

### 5-3. 差別化を「体験価値」で表現する

最も近い「大家さんのための超簡単！青色申告（家賃管理表）」と、MVPの体験を比べると次のとおり。

| 作業 | 大家さんのための超簡単！青色申告 | このアプリ（MVP） |
| --- | --- | --- |
| 報告書からの入力 | 入居者ごとの欄に、月ごとの金額を入力する | 報告書と同じ「1か月分・全室」の並びで、1画面に入力する |
| 変化がない月の登録 | 1月分を入力したあと、コピーボタンで下の月へ賃料をコピーする | 前月の内容が初期表示され、確認して保存するだけ |
| 入居者の交代 | 退室に変更し、入替行を追加する。年末退去で敷金の返還が翌年になる場合は、状態の切り替えや帳簿での個別処理が必要 | 新しい契約を入居日付きで登録するだけで、その月の入力画面に旧・新の両方の行が出る。敷金の残高は受領・返還の日付から自動で計算される |

- **私のアプリの差別化ポイント**：
  管理会社に任せている会社員大家が、届いた月次報告書を同じ並びのまま登録するだけで、入居者の入れ替わりや敷金の残高まで反映された「収入の内訳」が完成している。

## 7. このアプリで実現すること

### MVPの範囲

- MVPが支援するのは、入金実績の集計ではなく、**申告への転記に使える「不動産所得の収入の内訳」の作成**まで。
- 登録する金額は、管理会社からの振込額ではなく、月次報告書「収入の部」に載っている**入居者ごとの金額**とする。
- 経費・減価償却・損益計算書は、本リリースで対応する。

### 入力する項目と「収入の内訳」の対応

| 入力する項目 | 「収入の内訳」の反映先 |
| --- | --- |
| 物件・部屋：所在地、部屋番号、貸付面積、用途 | 不動産の所在地、貸付面積、用途 |
| 入居者（契約）：氏名、契約期間、月額賃料・共益費 | 賃借人の氏名、賃貸契約期間、賃貸料（月額） |
| 月次の金額：賃料・共益費・駐車料 | 賃貸料（年額） |
| 月次の金額：礼金・権利金・更新料 | 礼金・権利金・更新料 |
| 月次の金額：その他の収入 | 名義書換料その他 |
| 月次の金額：敷金・保証金の受領 | 収入には含めず、保証金・敷金（期末残高）に反映 |
| 敷金の返還・償却（返還不要分） | 保証金・敷金（期末残高）から差し引く。償却分は名義書換料その他に計上 |
| 管理会社への支払い・振込額 | MVPでは登録しない |

### 収入に計上する時期の扱い

国税庁の取扱いでは、家賃は契約上の支払日、礼金・更新料などは物件の引渡し日（または契約の効力発生日）、返還しない敷金は返還しないことが確定した日に、収入に計上する。入金された時期と、申告上の計上時期が異なる場合がある。

- **MVPで対応する範囲**：登録する金額ごとに「計上年月」を持たせ、初期値は報告書の対象年月とする。集計は入金日ではなく計上年月で行う。
- **利用者が確認・補正する範囲**：年をまたぐケース（12月に受け取った翌年1月分の家賃、12月分の滞納など）は、計上年月を修正するか、行を追加して補正する。集計画面で、12月分と翌年1月分の計上年月を確認するよう表示する。
- **対象外**：継続的な記帳による期間対応の特例、サブリース、敷金の未払家賃への充当などの例外処理。

### 入居者の交代と敷金の扱い

- **月次入力の行は、部屋ごとではなく契約ごと**とする。入居日から退去日までの期間がその月にかかる契約が、入力画面に1行ずつ並ぶ。
  - 同じ月に同じ部屋で入居者が交代した場合は、旧入居者と新入居者の2行が並び、それぞれの金額がそれぞれの契約の年額に集計される。
- **敷金は、契約ごとに「受領・返還・償却」を日付付きで記録する**。
  - その年の期末残高 ＝ 年末までに受領した額 − 年末までに返還・償却した額
  - 退去日ではなく、実際に返還・精算した日付で判断する。年末に退去して返還が翌年になった場合は、その年の期末残高に残る。
  - 翌年に返還を登録しても、前年末の残高は変わらないため、過去の年の「収入の内訳」をいつでも再現できる。

### MVPで作る機能

- ユーザー登録・ログイン
- 物件・部屋の登録
- 入居者（賃貸契約）の登録：氏名、契約期間、入居日、退去日、月額賃料・共益費
- 月次の金額の登録：契約ごとの行を1画面にまとめて入力し、前月の内容を初期値として表示する
- 敷金の受領・返還・償却の記録
- 「不動産所得の収入の内訳」の集計表示：決算書と同じ列の並びで、入居者ごとに表示する

### 本リリースで作る機能

- 月次収支報告書（PDF）をアップロードすると、LLMが内容を読み取って登録フォームに下書きを入れる（確認・修正してから保存）
- 経費・領収書の登録と集計（LLMによる領収書の読み取りを含む）
- 損益計算書の集計表示
- 入居者の入れ替わりや家賃の変更を、前月との差分としてハイライトする
- 前年から入居が続いている入居者の情報を、翌年に引き継ぐ
- 集計結果のCSV・PDF出力
- 複数物件への対応
- 月次報告書が届く時期に、登録を促すリマインドメールを送る

## 8. このアプリの懸念点とその対策

### 懸念点①　計算結果が間違っている可能性

- **何が問題になりそうか**：税金に関わる数字なので、計上時期や敷金の残高の扱いを誤ると、申告ミスにつながる。
- **なぜそう思うか**：入居者の交代や年をまたぐ入金は、自分自身も手作業で一番間違えやすいところだから。
- **そのために考えている対策**：
  - 過去に自分が提出した決算書の数字を再現できるかを、RSpecのテストで確認する。
  - 自動で判断する範囲と、利用者が確認・補正する範囲を分け、補正が必要な箇所（年をまたぐ月）を画面で知らせる。
  - 画面に「計算結果は最終的にご自身で確認してください」と明記する。

### 懸念点②　自分以外に使う人がいるか分からない

- **何が問題になりそうか**：周りに同じ立場の大家がおらず、需要を確かめられていない。
- **なぜそう思うか**：不動産を持つ会社員が身近にいないため、自分の悩みが一般的なものか判断できない。
- **そのために考えている対策**：まず自分が実際の確定申告で使い、効果を確かめる。あわせて、大家向けのコミュニティやSNSでリリースを告知し、フィードバックを集める。

### 懸念点③　入居者の個人情報の扱い（本リリースのLLM連携時）

- **何が問題になりそうか**：月次報告書には入居者の氏名が含まれ、LLMのAPIに外部送信することになる。
- **なぜそう思うか**：自分の情報ではなく、第三者の個人情報であるため。
- **そのために考えている対策**：入力データを学習に使わない設定のAPIを利用し、アップロードしたPDFは読み取り後に削除できるようにする。プライバシーポリシーに送信先と用途を明記する。

### 懸念点④　管理会社ごとに報告書の書式が違う

- **何が問題になりそうか**：決まった書式にしか対応できないと、他の大家が使えない。
- **なぜそう思うか**：月次報告書は管理会社ごとの独自書式であるため。
- **そのために考えている対策**：MVPは手入力にして、書式に依存しないデータ構造を先に固める。本リリースでは、書式に頼らず読み取れるLLMの強みを活かす。

## 9. 今後の展開・発展の方向性

### 観点

- **ユーザーはなぜ使い続ける？**：確定申告は毎年必ずやってくる。前年の物件・入居者・敷金の情報が引き継がれるため、2年目以降はさらに楽になる。
- **データが溜まると何ができる？**：入居率や家賃の推移を振り返れるようになり、家賃の見直しや修繕の計画に使える。
- **運用・仕組みで価値を出せないか？**：月次報告書が届く時期にリマインドを送り、登録を習慣にする。

### 今考えている発展案

- **機能追加の方向性**：LLMによる報告書・領収書の自動読み取り、経費を加えた損益計算書の作成、複数物件への対応
- **UI・体験の改善**：報告書と登録内容を左右に並べて確認できる画面、前月から変わった部分のハイライト
- **機能以外の工夫**：大家向けコミュニティでのフィードバック収集

## 10. 技術スタック（手段としての技術）

### 10-1. 使用予定の技術

- **フレームワーク**：Ruby 3.4 / Ruby on Rails 8.1（Hotwire）
- **DB**：PostgreSQL
- **デプロイ先**：Render
- **使用予定ライブラリ**：
  - MVP：Rails標準の認証ジェネレーター、Tailwind CSS、RSpec
  - 本リリース：Active Storage、Solid Queue、RubyLLM

### 10-2. 技術選定の比較検討

| 候補 | 採用/不採用 | 理由 |
| --- | --- | --- |
| Rails 8.1 + Hotwire | 採用 | カリキュラムで学んだRailsを活かせる。サポート期間内の最新版のため |
| React / Next.js | 不採用（MVP時点） | フォーム入力と集計表示が中心でHotwireで十分。学習コストが大きいため |
| LLM（本リリース） | 採用予定 | 管理会社ごとに書式が違う報告書でも、表の意味まで読み取れるため |
| OCR（文字認識）のみ | 不採用 | 文字は読めても、どの数字が誰の賃料かまでは解釈できないため |

- **今回チャレンジしたい点**：入居者の交代・計上年月・敷金の残高を含む集計ロジックを、テストで正しさを確認しながら作ること
- **不安な点**：LLMの読み取り精度とAPIの利用料金、カリキュラムで扱っていない技術のキャッチアップ

### 10-3. キャッチアップ不足の懸念

- MVPは、カリキュラムで学んだRailsとRSpecの範囲で作れる機能に絞った。
- LLMの連携は、MVPの完成後に小さなスクリプトで読み取り精度と料金を確かめてから、アプリに組み込むかを判断する。
